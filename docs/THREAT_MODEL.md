# Threat model

Scope: the protocol (`packages/protocol`), the server (`apps/server`), the merchant PWA (`apps/pos`) and the SANDBOX customer simulator (`apps/customer-sim`). Written for M6 (2026-11-17). Every mitigation below names the automated test that proves it; `pnpm security:matrix` fails if a named test file or test name does not exist, and `pnpm test:security` runs exactly the unit tests this table names.

Evidence words: "test" means an automated test in this repository that passes in `pnpm test` (or in the Playwright e2e, marked e2e). "NOT RUN" means no test or manual check exists.

## Assets

| Asset | Where it lives | Why it matters |
|---|---|---|
| Device secret (32 bytes) and its three derived keys (enc, code, auth) | Server: sealed at rest (AES-256-GCM under the master key). Phone: only the derived keys, as non-extractable CryptoKeys in IndexedDB | Whoever holds them can create sales, compute confirm codes and sign device requests for that merchant |
| Server master key | Server environment (`JAAY_MASTER_KEY`), never in the database | Opens every sealed secret in the database |
| Wallet connection (NWC string or LNbits invoice key) | Server, sealed at rest | Lets the server create and look up invoices on the merchant's wallet. Receive only by design |
| Confirm code (6 digits per sale) | Derived on demand; never stored, never in the QR payload | The merchant's offline proof that the customer paid |
| Receipt token (128 bits per sale) | Customer's receipt link; server stores only its SHA-256 and a sealed copy | Unlocks the receipt page and, after settlement, the code |
| Sale ledger | Phone (IndexedDB) and server (SQLite) | Merchant's books; reconcile compares the two |
| Merchant funds | The merchant's own Lightning wallet, never on Jaay | Jaay never holds or moves funds |

## Actors

- **Customer**: scans the QR with their own Lightning wallet, pays, opens the receipt, reads the code to the merchant.
- **Merchant**: runs the PWA on their phone, types the price and the code.
- **Malicious customer**: wants goods without paying (fake code, replay, guess, reuse another receipt).
- **Malicious merchant device**: a modified PWA or a script holding one device's keys; wants other merchants' data or to break the server.
- **Network attacker**: on the path between phone, customer wallet and server; can drop, delay, replay and read unencrypted traffic.
- **Server operator**: runs the Jaay server; sees amounts and sale metadata.
- **Thief**: holds a stolen merchant phone, locked or unlocked.
- **Supply-chain attacker**: ships malicious code through a dependency.

## Trust boundaries

```
 Merchant phone (offline OK)             Customer phone                    Jaay server (HTTPS)              Merchant wallet
 +------------------------------+        +---------------------+          +------------------------------+  +----------------+
 | PWA, keys non-extractable    |  QR    | any LNURL-pay       |  HTTPS   | LNURL endpoints (public)     |  | NWC or LNbits  |
 | sale = AES-GCM(amount, sid)  |------->| wallet              |--------->| receipt pages (public)       |->| receive only:  |
 | code check, 3 attempts       |        | pays the invoice    |<---------| device API (HMAC-signed)     |  | make_invoice,  |
 | ledger in IndexedDB          |        | opens receipt link  |          | SQLite, secrets sealed       |  | lookup_invoice |
 +------------------------------+        +---------------------+          +------------------------------+  +----------------+
        |  reconcile (signed), when online                                     ^
        +----------------------------------------------------------------------+
 B1: QR on the counter (anyone can photograph or replace it)
 B2: public internet to the server (LNURL, receipts): untrusted input
 B3: device API: trusted only after the HMAC check, server clock decides
 B4: server to wallet: the wallet enforces what the connection may do
 B5: browser origin /app/: any script there can use the keys, so the CSP is load-bearing
```

## Known limits stated plainly

- Offline confirmation relies on the code. Reconcile is the backstop: it detects a fraud after the phone is back online; it does not prevent it.
- The merchant secret on a stolen unlocked phone can create invoices only to the merchant's own wallet and cannot spend.
- The server operator sees amounts and sale times. Self-hosting is the answer for merchants who do not want that.
- JS constant-time comparison is best effort.

## What Jaay does NOT claim

- **Not custodial-safe against the wallet.** Funds live in the merchant's wallet. If that wallet or its provider is compromised, Jaay cannot help.
- **No protection from a compromised merchant device.** Malware or a modified browser on the phone can use the keys.
- **No anonymity.** The server sees amounts, times and device ids; the Lightning payment has the privacy of the customer's wallet and route.
- **Receive-only is enforced by the wallet, not by the protocol.** Jaay refuses spend-capable connections at enrollment and reports any spend permission later, but only the wallet service can actually stop a payment.
- **The demo is SANDBOX only.** The hosted demo and `pnpm demo` simulate payments; no real bitcoin moves. Real Lightning was exercised on regtest only (spike S1).
